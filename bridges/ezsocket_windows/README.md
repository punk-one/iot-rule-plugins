# EZSocket Windows read bridge

Independent Windows executable, not a Linux .so plugin. Requires operator-installed licensed EZSocket COM server and matching executable bitness (windows/amd64 or windows/386). Neither COM DLL nor vendor SDK is distributed. Configure a verified ProgID, exact Open arguments and read method aliases from the installed vendor documentation. The example intentionally uses placeholders: the old application's guessed NC type codes/Open signature are not accepted as proof. Configuration is trusted operator code; a Get/Read name prefix is an additional restriction, not a proof about a vendor method's semantics.

Set BRIDGE_TOKEN (32..256 characters) in the service environment, run `ezsocket-bridge.exe -config bridge.json`. Loopback HTTP by default; non-loopback listening requires TLS. Do not publish the endpoint anonymously. GET /v1/devices/{code}/telemetry returns {schema_version:1,device_code,data,quality,time}. No write/file/program endpoint. Alias/method names never come from the request. COM objects, calls and cleanup remain on one locked OS thread; one batch opens one object and releases it after all reads. Bounded request queue4 and finite HTTP deadlines. COM calls cannot be forcibly canceled: a hung vendor server can occupy the worker, at which point requests time out/fail instead of creating unlimited threads; service supervision must restart the isolated bridge.

Linux engine: bind connect-http to this HTTPS origin with Bearer token, then source-ezsocket-bridge. The Source validates the device identity and envelope, preserving quality. No DLL is loaded by the Linux engine. Linux HTTP tests use a synthetic reader; Windows cross-builds do not constitute COM/device acceptance.
