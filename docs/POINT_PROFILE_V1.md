# Point profile v1 and engineering values

The Engine point editor supports native JSON plus versioned Profile JSON/Excel for named point arrays. Profile version is `iot-rule-point-profile/v1` with an exact plugin ID. It maps common spelling aliases (value_type/valueType, read_write/readWrite, max_length/maxLength, byte_order/byteOrder, unit_id/unitId, node_id/nodeId, namespace_uri/namespaceUri) and preserves all declared protocol-specific fields/types. It does not guess addresses, offsets, units or unsupported fields. Another plugin's profile is rejected instead of silently converted. The runtime config remains each plugin's native schema; SDK v1 is unchanged.

Workbook cells use JSON-typed values, preserve nested range policies, and reject formulas/duplicate headers/unsafe integers/oversized ZIP/XML models before applying. Existing S7 native workbooks remain supported, including offset. Canonical JSON editing is used for all named point arrays rather than rendering thousands of repeated form rows. Source cadence stays explicit in node config; multiple rates use separate Sources and the shared Engine coordinator.

S7, Modbus and MC numeric pipelines use raw*scale+offset → range classification → precision. Replacement/default/clamped/dropped values retain bad quality. Numeric defaults must be finite and inside configured limits; replacement values also pass through rounding. Protocol-supported ranges/policies still differ and are validated, not invented by the editor. Read/permission failures are not substituted with fabricated good values. See the Engine docs/POINT_PROFILE_V1.md and docs/COORDINATED_POINT_SCANS.md for schemas, limits and mode compatibility.
