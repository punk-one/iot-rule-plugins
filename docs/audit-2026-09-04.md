# iot-rule-plugins 可靠性、稳定性与可扩展性审计

- 审计日期：2026-09-04
- 审计基线：`5ffaca9`
- 范围：19 个默认官方插件、构建脚本、FANUC 共享适配层、测试与发布治理
- 限制：未连接真实 MQTT、Redis、PostgreSQL、TimescaleDB、TDengine 或 FANUC 设备进行长稳测试

> 阅读说明：第 1～5 节保留整改前的审计基线和原始评级，便于追溯；当前整改结果
> 以第 7 节为准。代码侧 PLG-001～PLG-009 已完成或按项目隔离原则关闭，19 个
> 独立 module 已分别通过 test/race/vet/build。公开发布仍必须补签名产物，并在发布
> 环境执行真实服务与设备长稳测试，不能用本地 fake 测试替代。

## 1. 结论

仓库拆分方向正确：官方插件只引用公共 SDK，没有引用 `iot-rule-engine/internal`；默认 19 个插件全部能构建到独立可执行文件。Connector/Source/Sink 的 family 与 capability 约束，以及结构化错误和健康上报，为后续扩展提供了可用基础。

当前不宜直接作为自动发布仓库：全仓测试依赖未入库的 FANUC 专有 SDK；Source 停止流程存在已由 race detector 证实的生产字段竞态；TDengine 上游驱动不能通过当前 Go 版本的 `-race/checkptr`；构建产物没有 manifest、校验和、签名或 SBOM。

| 维度 | 评级 | 判断 |
| --- | --- | --- |
| 可靠性 | C | 默认构建成功，但 Source 生命周期竞态与 Ack/Nack 错误丢失会影响交付语义 |
| 稳定性 | C+ | 单元测试覆盖主要插件，但全仓门禁不可复现，版本与 artifact 缺少强绑定 |
| 可扩展性 | B- | 目录边界直观；共享 go.mod、复制实现和正则抽取元数据会随插件数增长放大维护成本 |

## 3. 分级发现

### PLG-001（P1）MQTT 与 Redis Source 停止流程存在真实数据竞态

证据：

- `sources/source_mqtt/plugin.go` 的 `Stop()` 关闭通道、读取/关闭并写空 `stream`；`handler.go` 的消费协程同时读取和写入同一字段。
- `sources/source_redis` 存在同构实现。
- race detector 明确报告 `Stop()` 与 `consumeLoop()` 对 `stream` 的并发读写。
- Stop 没有 WaitGroup，也没有等待消费和资源事件协程退出。

影响：停止、升级或连接异常重建时可能出现重复 Close、nil 访问、关闭后继续发布、状态顺序颠倒；也会削弱引擎热升级可靠性。

建议：每个 Source 使用单一生命周期 context、`sync.Once` 和 WaitGroup；stream 的创建/替换/关闭必须由单一协程拥有或加锁；Stop 应幂等并等待后台协程退出。对 PostgreSQL/TimescaleDB 的轮询 Source 同样补关闭并发测试。

整改状态（2026-09-05）：MQTT 与 Redis Source 已增加受锁保护的 stream 所有权、
`sync.Once` 幂等 Stop、WaitGroup 后台协程排空和停止状态检查；对应包
`go test -race` 已通过。

### PLG-002（P1）流消息 Ack/Nack 失败被忽略

证据：MQTT 和 Redis Source 的 `consumeLoop()` 对 `stream.Ack()`、`Nack()` 和错误后的 `Close()` 使用 `_ =` 忽略返回错误。

影响：插件可能已经发布事件，但确认失败导致重复投递；或 Nack 失败导致消息悬挂。插件仍上报 heartbeat，运维面看起来健康，实际交付语义已偏离。

建议：定义 Ack/Nack 重试、失败健康状态和停止策略；明确 Publish 成功但 Ack 失败时的幂等要求；增加断连和 Ack 超时测试。

整改状态（2026-09-05）：Ack/Nack 失败不再忽略；插件会上报结构化降级状态、
记录操作类型并关闭当前 stream，随后按现有退避策略重建 session。发布成功但 Ack
失败仍可能发生 at-least-once 重投，业务下游必须按 Event/业务键保持幂等。

### PLG-003（P1）FANUC 依赖使全仓构建不可复现

证据：

- `fanucutil/focas.go` 在所有 `linux/amd64` 构建中启用，并通过相对路径引用 `fanuc_libs/fwlib32.h` 与专有 `.so`。
- 新仓库未包含该目录，也没有下载、校验、许可证或 CI 安装说明。
- 因此 `go test ./...`/覆盖率在标准 Linux 环境失败。
- FANUC 代码不在默认 19 个插件清单中，却仍阻断整个 module 的测试。

建议：将 FANUC 设为显式 build tag 或独立 module/repository；提供合法的 SDK 获取说明、版本与 SHA-256；无专有库环境使用可编译 stub；CI 分为通用矩阵与受控 FANUC runner。

### PLG-004（P1）TDengine 驱动阻断竞态门禁

证据：`go.mod` 把 TDengine driver 替换到 `v3.3.1`；在 Go 1.25 `-race` 下，该版本 `common.murmurHash32` 触发 checkptr fatal error。

影响：无法对 TDengine 插件进行统一竞态验证；unsafe 实现与当前工具链组合存在维护风险。

建议：验证上游已修复版本或隔离带有 unsafe 的 adapter；在升级前建立真实 TDengine 回归；CI 必须明确记录该例外，不能把全仓 race 标成通过。

### PLG-005（P1）构建产物缺少可验证发布清单

证据：`build-plugins.sh` 用正则从 Go 源码抽取 ID/Version，失败时静默回退 `1.0.0`；构建后只创建版本文件和 `latest` 软链，没有 manifest、SDK 版本、commit、Go 版本、校验和、签名或 SBOM。

影响：格式调整可能打包错误版本；无法回答某个生产二进制来自哪个提交和依赖集合；`latest` 软链不具备可审计性。

建议：为每个插件建立机器可读 manifest，并由测试校验 manifest 与 `PluginInfo` 一致；release 输出 SHA-256、SDK/commit/toolchain、SBOM 和签名；不允许元数据抽取失败后默认成功。

### PLG-006（P2）共享单一 go.mod 放大变更半径

证据：19 个 `package main` 与 FANUC 适配层共用一个 module，依赖集合与引擎原始依赖接近。

影响：某一个数据库/协议驱动升级会改变整个仓库的 module graph，并可能阻断无关插件的测试；难以按插件独立控制升级节奏。

建议：短期保留 monorepo，但按协议族划分内部依赖与 CI job；中期评估 Go workspace + 每插件/插件族 module。只有发布和依赖隔离收益明确时才拆 module，避免过度碎片化。

### PLG-007（P2）相似实现复制较多

证据：PostgreSQL 与 TimescaleDB 的 Connector、Source 和 Sink 结构高度相似；三个批量时序/关系 Sink 也共享大量缓冲与 flush 生命周期逻辑。

影响：修复关闭、超时、批量 flush 或健康语义时容易遗漏某个插件，产生行为漂移。

建议：只抽取稳定、无业务含义的内部组件，例如批量缓冲生命周期、SQL 行编码、退避；保留各插件的 schema、ID 和协议语义，避免形成新的公共 API。

### PLG-008（P2）测试深度分布不均

证据：排除 FANUC 后总覆盖率 45%；Connector PostgreSQL/TimescaleDB/TDengine 约 23%–25%，`iot_mes_mapping` 为 0%；当前测试多为 fake connector/validation，没有仓库级真实服务测试编排。

影响：网络重连、事务边界、重复投递、批量部分失败、schema 演进等真实故障缺少证据。

建议：按插件契约建立统一测试套件；为 MQTT/Redis/SQL/TDengine 增加容器化集成测试；覆盖 Start→运行→断连→恢复→Stop，以及重复消息、超时和批量部分失败。

### PLG-009（P2）仓库治理文件缺失

影响与建议：首个公开 release 前补 LICENSE、CI、SECURITY、CONTRIBUTING、支持矩阵和插件维护状态表。插件可能携带不同第三方/专有许可，必须在 SBOM 与 NOTICE 中体现。

## 4. 正面能力

- 默认 19 个插件在 Go 1.25 环境全部可构建。
- 所有正式插件只依赖公共 SDK，三仓边界成立。
- Connector family 和 capability 声明明确，Source/Sink 通过 `connector_ref` 解耦连接资源。
- 多数插件包含配置验证、结构化错误、健康状态和单元测试。
- Redis Connector 测试覆盖相对较高，MQTT/Redis Source 已覆盖流式 session、decode 与 Ack 基础路径。

## 5. 整改顺序

1. 修复 PLG-001、PLG-002，建立幂等 Stop 和交付确认契约。
2. 隔离 FANUC 构建条件，恢复标准环境 `go test ./...`。
3. 解决或隔离 TDengine race/checkptr 阻断。
4. 建立 manifest、校验和、签名、SBOM 和每插件 release 追踪。
5. 补真实服务集成测试和低覆盖插件测试。
6. 再评估模块拆分与共享内部组件，不应先为目录整洁做大规模重构。

## 6. SDK v1 同步复核（2026-09-05）

本轮在不改变插件业务协议的前提下完成 SDK v1 接入：

- 新增仓库级 SDK v1 兼容测试，固定握手版本、Event ID 格式与 Event Clone 隔离语义。
- MQTT、Redis Source 的 Stop 已幂等并等待后台协程退出，stream 生命周期受锁保护。
- Ack/Nack 失败会记录结构化错误、上报降级状态、关闭 session，并在可中断退避后重建。
- Stop 在退出前调用健康上报 Flush，降低最终 Stopped 状态丢失风险。
- 通用插件集 `go test -race` 与 `go vet` 通过；默认构建清单 19/19 成功。

PLG-001、PLG-002 已完成。PLG-003 至 PLG-009 仍是插件仓库自身的后续治理项，
其中 FANUC 专有依赖和 TDengine 上游 checkptr 问题仍需独立隔离，不能据此宣称全仓
`go test -race ./...` 已通过。它们不阻断本轮 SDK v1 同步，但在插件仓库公开发布前
仍应按第 5 节顺序处理。

## 8. Connector 生命周期整改复核（2026-09-08）

- `connect-s7` 已由永久缓存和绝对 `per_operation` 收敛为 `scheduled_reuse`：默认根据
  2 秒内的下一次真实采集需求决定复用，5s/20s 自动按批关闭，100ms/500ms 连续复用。
- S7 一个 `batch_read` 内部即使按协议上限拆成多个 `AGReadMulti`，仍只使用同一连接。
- 旧 `shared_duplex`、`split_rw` 配置继续接受并归一化为需求感知复用；显式
  `per_operation` 和复用窗口 0 仍可强制按批关闭。
- `source-s7` 不再因上一次状态为 disconnected 永久停止真实读取，而是按照已有退避
  策略继续尝试，恢复后可以自动回到 healthy。
- S7 Source 使用 latest-only 固定节拍并在停止时释放需求；Connector 增加资源级会话
  统计、最大 8 会话门禁和失败熔断，离线时不会按 100ms 频率持续拨号。
- MQTT 声明 `session:persistent`；Redis、PostgreSQL、TimescaleDB、TDengine 声明
  `session:pooled`；S7 声明 `session:scheduled_reuse` 与兼容的 `session:per_operation`。
- 全部独立插件已通过 `scripts/test-plugins.sh`，覆盖 test、race、vet、build 和 FANUC stub。

FANUC 尚无正式 `connect-fanuc` 插件；现有 `fanucutil.WithConnection` 已具备请求内
分配和释放 handle 的边界。正式插件落地时必须保持该短连接模型，并在受控 runner
验证专有 FOCAS 库。
